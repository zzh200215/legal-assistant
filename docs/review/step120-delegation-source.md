# 第一百二十步交付说明：通知中心区分代收来源

> 一句话：通知改发给代理有两条路径（全局请假 / 按事件类型），此前只记「谁被代收」分不出是哪条；这一步在事件上记下来源，通知中心给「请假代收 · X / 类型代收 · X」标签、按来源筛选，并在请假中给出提示条。总资产 1651.3 → **1653.5 KB**（+2.2 KB）。

- 前端：`views/Notifications.vue`、`utils/notificationDelegation.js`（+ 单测）、`tests/e2e/notifications-center.spec.js`
- 契约：OpenAPI **376 paths / 178 schemas / 28 error codes**；新增 1 个**可选** query 参数（non-breaking），snapshot 已重基线
- 迁移：**124 个**，head `20261114_0123`；MySQL 实库已升级并核验 `VARCHAR(16)`

## 1. 为什么

step114 起通知中心就有「代 X 接收」标签与 `delegated=true/false` 筛选，step115 又加了全局请假代理。但列表里所有代收长得一样：

- 请假代收是「我这段时间不在」，代理是临时的、有起止日期；
- 事件类型代收是「这一类事件长期交给同事」，可能是常态分工。

两者对代理的含义完全不同（前者要交还、后者不用），代理人看通知中心时却分不出来；请假人自己也看不到「我现在在请假、通知正在被代收」的状态。step119 腾出 48.7 KB 余量后，这一步把来源补上。

## 2. 做了什么

### 2.1 事件表记录来源（迁移 0123）

`legal_notification_events` 增加可空列：

```sql
on_behalf_of_source VARCHAR(16) NULL   -- leave=请假代收，event=按事件类型代收，NULL=本人/历史数据
```

- 与 `on_behalf_of_user_id` 同生命周期：没有代收人时一律写 NULL，避免出现「有来源没代收人」的脏值；
- 历史代收事件保持 NULL：上线前没有记录路径，**不猜测回填**，读接口把它们归为 `unknown`，列表显示「代收 · X」；
- 迁移幂等（列已存在则跳过），downgrade 直接删列。

### 2.2 解析时写入来源

`_effective_recipient` 的返回值从 `(代理, 原收件人)` 扩成 `(代理, 原收件人, 来源)`：

| 命中路径 | user_id | on_behalf_of_user_id | on_behalf_of_source |
| --- | --- | --- | --- |
| 全局请假（优先） | 请假代理 | 请假人 | `leave` |
| 事件类型代理 | 代理 | 原收件人 | `event` |
| 本人 | 本人 | NULL | NULL |

- 优先级与回退不变：无效请假（跨组织/停用/过期）先回退到事件类型代理，再回退本人，来源跟着实际命中走；
- 来源只影响展示与筛选，不参与幂等键：同一业务事件重放仍返回同一条记录；
- `allow_delegate=False` 的通知（代收开始/交还、请假人回执、升级）不经过这段解析，来源为空。

### 2.3 读接口

`GET /api/developer/notifications/me`：

- 新增可选 `delegation_source=leave|event|unknown`，与 `delegated` 可叠加；非法值 **422「代收来源不支持」**；
- 每条通知返回 `on_behalf_of_source`（本人为 `null`）；
- `unknown` 的口径是「有代收人但没有来源列」，只给接口/排障用，前端不给入口。

### 2.4 通知中心

| 位置 | 之前 | 现在 |
| --- | --- | --- |
| 代收标签 | 「代 张三 接收」 | 「请假代收 · 张三」/「类型代收 · 张三」/「代收 · 张三」（历史），请假用主色、其余中性色 |
| 来源筛选 | 全部 / 本人 / 代收 | 全部来源 / 本人 / 全部代收 / 请假代收 / 类型代收；后两项只发 `delegation_source`，不叠 `delegated` |
| 页头 | 无 | 本人请假中时给提示条：「请假中 · 代 协办律师 接收 · 2026-11-10 至 2026-11-20 · 剩余 9 天」+「调整请假」直达通知偏好 |

- 提示条只读：读取 `/notification-leave/me` 失败就静默隐藏，不影响列表加载；
- 标签文案与筛选参数抽到 `utils/notificationDelegation.js`（纯函数），配 4 条单测。

## 5. 边界

1. **历史代收不可追溯**：0123 之前创建的代收事件来源为空，一律显示「代收」，`unknown` 筛选也只在接口层可用；不按请假记录反推，避免张冠李戴。
2. **只区分两条路径**：来源是 `leave` / `event` 两个值，没有记「哪个事件类型的代理」；事件本身有 `event_type`，需要时可组合查询，但标签不展开。
3. **提示条只读**：不能在通知中心直接结束请假，必须去通知偏好页；提示条显示的是**当前用户自己**的请假，代理视角看不到请假人的状态。
4. **提示条静默失败**：`/notification-leave/me` 报错（如无组织）时整条隐藏，不提示错误，也不影响列表。
5. **来源创建时定格**：之后换代理、结束请假、修改有效期都不会改写历史事件的来源；这与「通知是历史记录」的口径一致。
6. **回执条数仍按「转发给请假人代理」计数**：包含代收开始/交还期间所有转发事件，不区分来源（请假优先，实际上都是请假代收）。
7. **包体仍在 97%**：这一项 +2.2 KB，余量 46.5 KB；95% 预警档还在，继续加 UI 前仍要先量产物。
8. **筛选项没有「历史代收」入口**：`unknown` 只给接口和排障，产品界面不暴露这个词，避免用户误解为一种可配置的来源。

## 6. 后续建议

- **代理视角的「我代收了谁」汇总**：代理人在通知中心只看得到零散标签，可加一个按请假人聚合的折叠区（本轮做了来源，下一步顺势做聚合）；
- **请假结束前提醒请假人**：现在到期提醒只提醒请假人「请假将结束」，可以顺带给出「本轮代理共代收 N 条」，与恢复回执口径一致；
- 若还想压包体，可评估 `@ctrl/tinycolor`（13 KB，仅 el-button 的 `color` 属性用、当前未使用）与 `el-input-number`（12 KB，仅两处数字输入），都需要产品确认。
