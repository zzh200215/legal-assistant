## 1. 触发条件

同时满足以下条件才升级：

1. 任务状态是 `todo` / `in_progress`，未归档，有截止日期；
2. 任务有负责人（`assignee_user_id` 非空）；
3. 按 **owner 自己的通知偏好时区** 计算，截止日期已过去 **3 天及以上**；
4. owner 不在普通提醒收件人里（收件人 = 负责人 + 协作者）；
5. 该任务还没有给这个 owner 发过升级提醒。

| 场景 | 是否升级 | 原因 |
| --- | --- | --- |
| 负责人 ≠ owner，逾期 ≥ 3 天 | 是 | 负责人/协作者没处理，owner 需要知道 |
| owner 就是负责人 | 否 | owner 已收到普通逾期提醒 |
| 没有负责人，只有协作者 | 否 | owner 是普通提醒的第一收件人 |
| owner 同时是协作者 | 否 | owner 会收到协作者提醒 |
| 逾期不足 3 天 | 否 | 还没到升级阈值 |
| 已完成 / 已取消 / 已归档 | 否 | 不在扫描范围 |

- 升级按 owner 时区判断，不跟着负责人时区走；owner 在东京、负责人在纽约时，东京先到第 3 天就先升级；
- 因为条件是「≥ 3 天」而不是「正好第 3 天」，即使 beat 停了几天、恢复后已经逾期 5 天，也会补发一次。

## 2. 去重与渠道

- 去重键：`(task_id, owner_id, task_owner_escalation_overdue_3d)`；
- 同一任务、同一 owner 只发一次，逾期 4/5/6 天不会重复刷；
- 任务转交 ownership 后，新 owner 可以各收一次；
- 渠道沿用 `deadline` 事件偏好：站内始终创建；邮件在组织配置外发策略、且 owner 未关闭 email 时进入 Outbox；
- 站内标题「任务逾期 N 天升级：任务标题」，正文带负责人姓名和协作者人数（0 人时省略「协作者 0 人」）；
- 站内通知与邮件按钮都直达 `/tasks?taskId=N`。

## 6. 边界

1. **阈值固定 3 天**：没有组织级或任务级配置。
2. **只有一级升级**：owner 再不处理，不会升级给部门管理员或更高层。
3. **只发一次**：升级后不会每周再催；后续提醒依赖人工或普通提醒。
4. **必须有负责人**：没有负责人的任务，owner 本身就是普通收件人，不重复升级。
5. **无组织任务跳过**：无法定位 owner 的通知偏好，沿用原逻辑。
6. **无前端改动**：通知中心已有任务深链，升级提醒复用同一路由，包体 0 变化。

## 7. 后续建议

- 组织级升级阈值与接收人（部门管理员 / 指定人）；
- 升级后仍未处理，按天/周再次提醒；
- 每日任务摘要，把「已升级」「仍逾期」聚合到一封邮件；
- 在任务详情显示升级记录（谁、何时、第几天）。
