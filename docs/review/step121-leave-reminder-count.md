# 第一百二十一步交付说明：请假到期提醒带上代收条数

> 一句话：请假人在到期前 2 天收到的提醒，原先只说「代理将于 X 到期」；现在补一句「本轮代理已代收 N 条」，与「已恢复」回执同一口径，让请假人在结束前就知道积压量。纯后端改动，总资产 **1653.5 KB 不变**。

- 日期：2026-11-14
- 后端：`services/jobs/delegate_reminders.py`、`services/notification/notification_service.py`
- 前端：无改动
- 契约：OpenAPI **376 paths / 178 schemas / 28 error codes**（无接口变化）
- 迁移：**无新增**（仍 124 个，head `20261114_0123`）
- 测试：后端 `test_leave_expiry_reminder.py` 12 → **14**；前端单测 124 / e2e 23 不变

---

## 1. 为什么

step118 把「本轮代收 N 条」放进了**请假结束后的「已恢复」回执**——通知是准的，但已经晚了：请假人看到时假已经结束，没法据此安排收尾或提前结束请假。

到期提醒是**结束前 2 天**发的，正是能行动的时点。这一步把同一个数字挪到提醒里：

- 请假人提前知道「这轮积压了 7 条」，可以决定提前回来、延长请假，或先让代理处理重点；
- 与恢复回执共用同一个计数函数，不会出现「提醒说 5 条、恢复说 7 条」的自相矛盾。

## 2. 做了什么

### 2.1 计数函数公开

`notification_service._leave_period_forwarded_count` 外面加一层公开方法 `leave_period_forwarded_count`，口径完全复用：

- 起点是「已生效」回执（它创建的时刻就是转发开始），不是请假开始日期；
- 用事件 id 递增划分轮次，上一轮请假的事件 id 更小，不会混进本轮；
- 只数站内通知（`channel=site`），与恢复回执一致。

### 2.2 提醒正文

`_scan_leave` 在拼正文前取一次计数：

| 情况 | 正文片段 |
| --- | --- |
| 有代收 | `本轮代理已代收 7 条通知` |
| 没有代收 | `本轮还没有需要转发的通知` |

完整正文示例：

```
leave:expiring · 请假代理 代理律师 将于2 天后到期（2026-11-12），
本轮代理已代收 7 条通知，之后的通知恢复发送给你
```

- 站内与邮件共用同一段正文，两端数字一致；邮件模板 `leave_expiring_soon` 的 lead/footnote 未改；
- 0 条时不写「0 条」，避免读起来像统计失败。

## 5. 边界

1. **只数站内通知**：与「已恢复」回执同口径，邮件/微信投递不计入——它们是同一业务事件的其他渠道，重复计数会虚高。
2. **以「已生效」回执划界**：请假真正开始前没有回执，计数为 0；上线前开始、上线后才结束的请假会在恢复回执里看到 0 条（step118 既有口径，未变）。
3. **只给请假人本人**：提醒 `allow_delegate=False`，不会转给代理，代理看不到请假人的积压数。
4. **每天只提醒一次**：按结束日期去重；改结束日期会重新提醒，并带上当时的**最新**条数（数字会变，不是历史快照）。
5. **代理的「已交还」通知仍不带条数**：本轮只改请假人侧；代理若需要汇总，见后续建议。
6. **无接口、无迁移、包体不变**：纯后端字段拼装，前端与契约零改动。

## 6. 后续建议

- **代理的「已交还」通知也带条数**：和请假人回执对称，让代理知道这轮帮人接了多少（同一函数，约 10 行 + 2 条测试）；
- 代理视角的「我代收了谁」聚合：按请假人分组展示，需要前端改动，当前包体 97% 需先量产物。
