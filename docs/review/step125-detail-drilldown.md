# 第一百二十五步交付说明：「查看明细」下钻

> 一句话：给「我代收了谁」的每行加一个「明细」按钮——点它清掉其它筛选、只留这位同事和当前时间窗，把列表带到视野里，并用一条「正在看 X 的代收，共 N 条」把上下文说清楚。总资产 1658.2 → **1659.0 KB**（+0.8 KB）。

- 日期：2026-11-14
- 前端：`views/Notifications.vue`、`tests/e2e/notifications-center.spec.js`
- 后端：无改动（复用 step123 的 `delegated_from_user_id` 与 step124 的 `days`）
- 契约：OpenAPI **377 paths / 178 schemas / 28 error codes**（无接口变化）
- 迁移：**无新增**（仍 124 个，head `20261114_0123`）
- 测试：前端单测 124 不变；e2e 24（扩展既有用例）

---

## 1. 为什么

step123 点分组是「在当前筛选上再加一个人」，step124 又叠了时间窗。两个功能叠加后有个实际问题：用户可能已经选了「未读 + 关键日期 + 请假代收」，再点某个人，看到的是**所有条件交集**下的一小撮——但他其实想看「这个人全部的代收」。

也就是：**快速筛选**（保留上下文）与**看明细**（清空上下文）是两种意图，之前只有前者。

## 2. 做了什么

| 入口 | 行为 |
| --- | --- |
| 行主体（姓名/条数/时间） | 保持「快速筛选」：只加这个人，其它筛选不动 |
| 行尾「明细」 | 清空状态 / 类型 / 来源 / 案件编号，只保留这个人 + 当前时间窗，重置到第 1 页，并把通知卡片滚到顶部 |
| 上下文条 | 从「只看代 X 的通知 · 清除」改为「正在看 **X** 的代收，共 N 条（近 7 天）· 返回全部」 |
| 返回 | 「返回全部」只清掉按人筛选，其它条件保留 |

实现要点：

- 行从 `<button>` 改成 `<div>` 包两个按钮（`pick` 与 `明细`），避免按钮套按钮的非法结构；行主体仍是点击热区；
- 明细按钮用 `nextTick` + `scrollIntoView({block:'start'})` 把列表带到视野，滚动是平滑的；
- 「共 N 条」取当前列表总数（`total`），不是汇总行里的历史条数——所以叠加筛选时数字仍然准确。

## 5. 边界

1. **明细只清筛选，不换页面**：仍是通知中心同一页，靠滚动定位；没有独立 URL，刷新后回到默认列表。
2. **时间窗保留**：明细保留当前「近 7/30 天」，因为窗口是页面级上下文；想跨全部时间要先切回「全部时间」。
3. **「共 N 条」是当前筛选的结果数**：如果之后再叠状态筛选，这个数字会跟着变，不是固定快照。
4. **滚动依赖浏览器平滑滚动**：`prefers-reduced-motion` 下由浏览器自行降级，没有单独处理。
5. **汇总行仍是两个人操作区**：点主体=快速筛选、点明细=清空后看；两个按钮紧邻，触屏上要注意误触（未做二次确认）。
6. **包体 98%**：这一项 +0.8 KB，余量 41.0 KB；后续动 UI 前仍需先量产物。

## 6. 后续建议

- **把明细状态写进 URL**（`?delegated_from=16&days=7`）：刷新与分享都能保留上下文，也能让「返回全部」用浏览器后退；
- **包体治理**：余量只剩 41.0 KB，`@ctrl/tinycolor`（13 KB，仅 el-button 的 `color` 属性用、当前未使用）与 `el-input-number`（12 KB）都可评估，一次性把预算拉回 95% 以下；
- 若继续做通知：给汇总行加「按事件类型分布」的小色条，回答「这个人主要是什么类型的通知」。
