## 1. 行为

`create_multi_channel_notification(allow_delegate=True)`（默认开启）：

1. 读取原收件人的事件偏好；
2. 若配置了 `delegate_user_id`，且代理是同组织、`active`、不是本人：
   - 事件 `user_id` = 代理；
   - `on_behalf_of_user_id` = 原收件人；
   - 正文前缀「（代 X 接收）」；
   - 渠道与静默按**代理自己的偏好**解析；
3. 否则按原收件人发送；
4. 代理只跳一层：代理自己的 `delegate_user_id` 不再继续转发；
5. 代理无效/停用/跨组织/指向自己时回退原收件人，不报错。

| 场景 | 结果 |
| --- | --- |
| 原收件人配置有效代理 | 代理收到站内/邮件，原收件人不再收到这一条 |
| 代理已停用 / 跨组织 / 不存在 | 回退原收件人 |
| 代理指向自己 | 回退原收件人 |
| 代理也配置了代理 | 只发给第一层代理，不链式转发 |
| 任务逾期升级 | `allow_delegate=False`，直达 owner |
| 投递告警 | `allow_delegate=False`，直达管理员 |

## 2. 去重与审计

- 幂等键在原有 `组织:收件人:渠道:事件:引用:版本[:模板]` 后追加 `for:原收件人`，避免多个人的同类事件在同一个代理处互相覆盖；
- `legal_notification_events.on_behalf_of_user_id`（迁移 0119）记录原收件人，API 序列化下发；
- 任务提醒扫描用 `on_behalf_of_user_id` 还原原收件人做去重，代理事件不会因为「收件人变了」被每轮重复创建；
- 正文前缀让代理知道这条是代谁接收；事件 `user_id` 仍是代理，权限与已读状态按代理本人计算。

## 6. 边界

1. **代理不改变资源权限**：代理能收到通知，但打开任务/咨询/案件仍按代理本人的权限判定；同组织通常可见，跨部门/共享范围仍可能 403。
2. **只代理一跳**：不支持 A→B→C 链式转发，避免环和失控。
3. **创建时解析一次**：事件创建后代理被停用/改派，已有事件不会自动改投或撤回。
4. **强提醒不代理**：任务逾期升级、投递告警始终直达本人/管理员。
5. **没有代理关系管理页**：代理只能按事件类型单独设置，没有“请假期间全局代理”。
6. **没有代收审计 UI**：字段已在 API 下发，通知中心暂未展示「代 X 接收」标签（正文有前缀）。
7. **摘要频率仍只是存储**：没有汇总任务消费。

## 7. 后续建议

- 通知中心展示「代 X 接收」标签，并支持按代理筛选；
- 全局代理（请假模式）与代理有效期；
- 代理变更时重投未读事件；
- 摘要任务按 `summary_frequency` 聚合。
