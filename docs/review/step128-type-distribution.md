# 第一百二十八步交付说明：代收汇总的类型分布条

> 一句话：「我代收了谁」每行多一条类型分布条——按工作流 / 关键日期 / 审核 / 门户 / 账单的条数比例分段，悬停显示「类型 N 条」。总资产 1639.7 → **1640.6 KB**（+0.9 KB）。

- 日期：2026-11-16
- 后端：`services/notification/notification_service.py`、`api/developer/notifications_onboarding.py`
- 前端：`views/Notifications.vue`、`tests/e2e/notifications-center.spec.js`
- 契约：OpenAPI **377 paths / 178 schemas / 28 error codes**（响应为自由 dict，无 schema 变化）
- 迁移：**无新增**（仍 124 个，head `20261114_0123`）
- 测试：后端 2709 → **2710**；前端单测 129 不变；e2e 25（既有用例扩展）

---

## 1. 为什么

step123 的汇总只回答「代收了几条」，step124 加了时间窗，step125/127 补了下钻与分享；但代理人仍然不知道**这些通知是什么类型**——「主办律师那 7 条」里可能是 5 条关键日期 + 2 条审核，也可能是全审核，处理方式完全不同。

类型分布条用一眼能看懂的方式回答「这个人主要是什么类型的通知」，且不增加点击成本。

## 2. 做了什么

### 2.1 后端

`delegated_summary` 在原有聚合之外，多跑一条 `GROUP BY origin_id, event_type` 的查询，把结果挂到每个人：

```json
{"user_id": 15, "count": 7, "unread": 2, "last_at": "...",
 "types": [{"event_type": "approval", "count": 4},
           {"event_type": "deadline", "count": 3}]}
```

- 与主汇总**共用同一组过滤条件与天数窗口**，所以 `sum(types.count) == count`；
- 排序：条数降序 → 类型名升序，保证颜色段顺序稳定；
- 只多一次分组查询（不是每人一次），人数上限 50 不受影响。

### 2.2 前端

- 行内加一条 3px 高的分段条，段宽按条数比例（`flex-grow`），最少 3px；
- 颜色固定映射：工作流=绿、关键日期=主色、审核=橙、客户门户=灰、账单=红；
- 悬停用原生 `title`（「审核 4 条」），不引入 tooltip 组件；
- 条在窄屏同样占满整行（`grid-column: 1 / -1`）。

## 5. 边界

1. **颜色是固定映射，不是主题色**：绿/主色/橙/灰/红对应五种事件类型，与状态色无关；看惯了「红=错误」的人可能误读账单段，悬停文案是唯一解释。
2. **段宽按条数比例**：某一类只有 1 条时会被压到最小 3px，比例感会失真；这是为了避免「1 条也占一大段」。
3. **悬停只有原生 tooltip**：移动端没有悬停，看不到各类型的具体条数。
4. **仍只统计站内、非失败、同一时间窗**：与汇总数字严格一致，邮件/微信不计入。
5. **`types` 只出现在汇总接口**：通知列表的每一行不带类型分布，避免列表接口变重。
6. **包体脚本显示 97%**：实际 1640.6/1700 = 96.5%，脚本取整后显示 97%，95% 预警档仍在。
