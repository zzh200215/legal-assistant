# 第一百一十三步交付说明：代理到期后自动清理

> 一句话：每日代理扫描顺带清理已过期的设置——清空 `delegate_user_id`、`delegate_start`、`delegate_end`，避免「代理已失效但设置还挂着」；同时约定「没有代理就没有有效期」，API 清空代理时一起清日期。

## 1. 行为

每日 09:10 的 `check_delegate_expiring` 现在分两段：

| 条件 | 动作 |
| --- | --- |
| `delegate_end < 当地今天` | 清空 `delegate_user_id`、`delegate_start`、`delegate_end`，`cleared += 1` |
| `0 ≤ 剩余天数 ≤ 2` | 按 step112 提醒原收件人一次 |
| 剩余天数 > 2 | 不动 |
| 没有代理或没有结束日期 | 不在扫描范围 |

- 清理后 `_effective_recipient` 自然回退原收件人，后续通知不再转给代理；
- 返回值新增 `cleared`：`{"created": N, "scanned": N, "cleared": N}`；
- 清理与提醒在同一轮完成：到期当天仍会提醒（`days=0`），次日清理。

## 2. API 不变量

`PUT /notification-preferences/me`：

- 显式 `delegate_user_id: null` 时，同时清空 `delegate_start` / `delegate_end`；
- 只传日期、不传代理时，日期也会被清掉；
- 避免页面出现「代理：不设置，却有一段有效期」的矛盾状态；
- 已有「开始晚于结束 → 422」校验保持不变。

## 5. 边界

1. **清理不写审计**：没有记录「哪天清理了谁的代理」，只能从通知/设置现状推断。
2. **依赖每日任务**：09:10 的 beat 停摆时，过期设置会一直留到下一次成功执行。
3. **清理即删除日期**：不保留历史有效期；如需追溯，只能查通知事件。
4. **不清理「无结束日期」的代理**：长期代理不会被自动关闭。
5. **不清理无效代理**：代理被停用/跨组织时，设置仍保留，只在投递时回退。
6. **没有提前通知清理结果**：到期前 2 天的提醒是唯一提示，清理本身不再发消息。
7. **无前端改动**：页面看到的就是清理后的空代理与空日期。

## 6. 后续建议

- 全局请假模式：一次设置所有事件类型的代理与有效期；
