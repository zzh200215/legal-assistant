# 第一百一十八步交付说明：恢复回执带上代收条数

> 一句话：「通知已恢复」回执里补上本轮请假期间由代理代收了多少条通知；按「已生效」回执划界，换代理只统计最后一位。

## 1. 为什么

上一步的「已恢复」回执只说「Bob 不再代收，通知恢复给你」，请假人回来时仍不知道：

- 自己不在的这段时间，到底有多少通知被代理处理；
- 是否需要主动找代理对一遍，还是可以直接回到自己的通知中心。

补一句「期间共 N 条通知由 Bob 代收」，让请假人有个判断依据，也让代理的代收劳动可见。

## 2. 计数口径

- **只数「通知」不数「渠道」**：按 `channel=site` 的事件计数，一封同时发站内 + 邮件只算 1 条；
- **只数真正转发的**：条件为 `on_behalf_of_user_id = 请假人`，代理自己的通知、系统回执都不计入；
- **按轮次划界**：起点取本轮「已生效」回执（它创建的时刻就是转发开始），并只数 `id` 大于该回执的事件，更早轮次的代收不会重复计入；
- **0 条也有话说**：`期间没有产生需要转发的通知`，而不是留空让人猜；
- 计数结果**写死在回执正文**里，回执创建后不随数据变化重算（幂等键保证只发一次）。

示例：

```
你的请假已结束，Bob 不再代收；期间共 12 条通知由 Bob 代收，之后的通知都会发给你本人。
你的请假已结束，Bob 不再代收；期间没有产生需要转发的通知，之后的通知都会发给你本人。
```

## 3. 边界

1. **只统计站内事件**：站内通知每条一事件、创建即 delivered，是最稳的「通知条数」口径；邮件渠道不重复计数。
2. **起点是回执而不是请假日期**：请假可能没有开始日期、也可能提前几天设置，用回执创建时刻更准。
3. **并发漏计**：极端情况下，设置请假的同一瞬间已经有一个转发事件在途，可能少算 1 条。
4. **换代理只算最后一位**：A → B 会开新轮次，恢复回执里的 N 只统计 B 代收的条数，A 期间的条数不在其中。
5. **回执不重算**：N 是创建时的快照；之后补发/重试的通知不会改变已经发出的数字。
6. **老请假没有回执**：上线前设置、没收到「已生效」回执的请假，结束时不发恢复回执，也就没有条数。
7. **不区分已读**：代理是否点开不影响计数。
8. **无迁移、无接口、无前端**：纯服务层文本与查询，包体维持 1689.1 / 1700 KB。

## 6. 后续建议

- 通知中心区分「请假代收 / 事件类型代收」，并给请假人一个「代收周报」入口（需先腾包体预算）；
- 恢复回执附「最早/最近一条代收通知」的深链，方便直接回看；
- 给代理的「已交还」也带上「你在这期间代收了 N 条」；
- 支持「提前回来」：结束请假时记录实际区间，代收条数与计划区间分开统计。
