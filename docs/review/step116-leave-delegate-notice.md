> 一句话：请假生效时通知代理「开始代收」，请假结束或换人时通知原代理「已交还」；按请假轮次去重，且不会被代理自己的代理设置转走。

## 1. 为什么

上一版请假只解决了「通知转给谁」，代理本人却不知道两件事：

- 从哪天开始要替同事收通知（特别是提前几天设好的请假，到点没人提醒代理）；
- 什么时候已经交还（结束请假、到期清理后，代理可能还在按旧习惯处理）。

结果是代理要么漏接，要么在请假结束后继续收到「以为还要管」的提醒。这一步把这两个时点补成两条明确的通知。

## 2. 触发时机

| 事件 | 收件人 | 时机 | 模板 |
| --- | --- | --- | --- |
| 开始代收 | 代理本人 | 设置时请假已生效 → 立即；未生效 → 到开始日的 09:10 扫描 | `leave_agent_started` |
| 已交还 | 原代理 | 手动结束请假、换代理、或到期清理时 | `leave_agent_ended` |

- 两条都是站内 + 邮件，走代理自己的渠道偏好与静默时段（非强提醒，命中静默只延后邮件）；
- 通知的 `user_id` 是代理，`on_behalf_of_user_id` 为空：这是代理「本人」的消息，不是代收事件，通知中心的「代收」筛选不会把它们算进去；
- 正文写明请假人姓名与起止（`2026-11-10 至 2026-11-20 请假`），代理不用回查设置。

## 3. 幂等：按「请假轮次」而不是日期

同一次请假里重复点保存、任务重复扫描都不应重复通知；但结束一次请假后再请一次，即使日期完全相同，也应该重新通知。只按日期去重做不到这一点，因此新增 `legal_notification_leaves.leave_period`：

- 代理发生变化（空 → 某人，或 A → B）时 +1；
- 代收开始/交还通知的幂等键用 `reference_type=notification_leave` + `reference_id=请假行` + `business_version=轮次` + 模板键；
- 只改日期、备注、重复保存同一代理：轮次不变，不重复通知。

迁移 **0122**：`leave_period INT NOT NULL DEFAULT 0`；MySQL 实库已升级并核验（默认值 0），SQLite 上单独验证 upgrade/downgrade（含历史行回填 0）。

## 4. 不转给代理的代理

两条通知都用 `allow_delegate=False` 创建：

- 「开始代收」如果被代理自己的请假/代理设置转走，代理就永远不知道自己该代收了；
- 「已交还」同理，必须直达原代理。

测试里专门覆盖：Bob 自己也把通知转给 Carol 时，Alice 请 Bob 代收，这条通知仍只发给 Bob（`user_id=Bob`、`on_behalf_of_user_id=NULL`）。

## 5. 边界

1. **只通知在职同组织代理**：代理被停用、跨组织或账号不存在时跳过，但请假设置本身照常保存（发送时也会回退本人）。
2. **取消未开始的请假不发交还**：只有代理确实收到过「开始代收」才发交还，避免「你已交还」但对方从没被告知要代收。
3. **改日期不重发**：轮次只在换代理/重新请假时 +1；请假期间延长结束日期不会给代理补发新通知（到期提醒仍会按新日期提醒本人）。
4. **换代理是单向的**：旧代理收到「已交还」，新代理收到「开始代收」，但不会撤回旧代理已经收到的转发通知（没有撤回机制）。
5. **借用 `deadline` 事件类型**：通知偏好里没有「系统/设置」事件类型，这两条走 `deadline` 的渠道配置；如果用户把关键日期渠道全关，代理只会收到站内。
6. **部署前已生效的请假**：轮次默认 0，上线后第一次扫描会给代理补发一条「开始代收」（内容正确，但对代理是一次迟到的提醒）。
7. **通知可被静默延后**：这是信息类通知，不是强提醒；命中静默时邮件延后，站内仍即时。
8. **无撤回、无已读门槛**：代理不点开也不影响转发；交还通知同样不要求确认。

## 8. 后续建议

- 通知中心区分「请假代收 / 事件类型代收」，并在请假中给出全局提示；
- 交还时给请假人一条「通知已恢复」的回执，形成闭环；
- 请假开始前 1 天给代理一个预告（现在是开始当天才通知）；
- 支持撤回：换代理时把旧代理未读的转发通知标注「已失效」。
