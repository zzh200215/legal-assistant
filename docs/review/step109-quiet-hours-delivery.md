# 第一百零九步交付说明：静默时段接入普通通知投递

> 一句话：命中用户静默窗口时，站内通知立即送达，邮件/微信/飞书等外部渠道不再直接发出，而是把 `scheduled_at` 推迟到窗口结束；逾期升级等强提醒显式穿透静默。

## 1. 行为

`create_multi_channel_notification` 新增 `respect_quiet_hours=True`（默认开启）：

1. 先解析实际渠道（站内始终包含）；
2. 若存在外部渠道、且用户偏好命中静默窗口：
   - 站内事件照旧立即创建并 `delivered`；
   - 外部渠道事件 `scheduled_at = next_quiet_end`，状态仍 `pending`；
   - 站内/邮件正文追加「（静默时段，外部渠道将于 HH:MM 后发送）」；
3. 不在窗口内、没有偏好、起止时间相同或非法时区，行为与之前完全一致；
4. Outbox 领取条件本来就带 `scheduled_at IS NULL OR scheduled_at <= now`，不需要改投递 worker。

`next_quiet_end` 的口径：

- 按用户偏好时区解释窗口，支持跨夜；
- 22:00–07:00 在 23:00 命中 → 次日 07:00；
- 22:00–07:00 在 01:00 命中 → 当天 07:00；
- 返回 UTC，写入 `scheduled_at`；
- 时区非法回退 UTC，不阻塞创建。

## 2. 穿透静默

以下强提醒显式传 `respect_quiet_hours=False`：

| 场景 | 行为 |
| --- | --- |
| 任务逾期升级 owner（step107） | 站内 + 邮件立即创建，正文不追加静默提示 |
| 投递告警升级（step43） | 保持原逻辑：普通告警降为站内，升级始终站内 + 邮件，正文不带静默提示 |
| 普通任务到期/协作者提醒 | 尊重静默，外部渠道延迟 |
| 审核/账单/签署/门户等普通通知 | 尊重静默，外部渠道延迟 |

投递告警自己用 `_channels_for` 决定渠道并拼静默文案，因此调用时传 `respect_quiet_hours=False`，避免被通用延迟逻辑再改一次。

## 5. 边界

1. **只延迟不丢弃**：窗口结束后仍会投递一次；如果 worker 停摆，实际到达时间会更晚。
2. **静默作用于所有外部渠道**：不只是邮件，微信/飞书事件也延迟；站内始终即时。
3. **只有显式强提醒穿透**：任务逾期升级、投递告警升级；其他通知一律尊重静默。
4. **`scheduled_at` 由静默窗口覆盖**：调用方同时传 `scheduled_at` 时，当前实现以静默结束为准；现有调用方都没有传。
5. **创建时算一次结束时间**：创建后用户再改偏好或时区，已建事件不会重排。
6. **修改偏好不会重排历史事件**：只影响之后创建的通知。
7. **无前端页面改动**：通知偏好页提示从「仅对告警生效」改为「站内立即、外部延后、升级穿透」。
