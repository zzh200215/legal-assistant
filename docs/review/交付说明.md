## 2. 为什么是「四层」而不是一个聊天框

法律场景的答复不能只要「说得像」，要能回答四个问题，分别对应四层：

1. **它做了什么？**（过程）→ 时间线：检索了几条、生成是否降级、核验跑没跑
2. **依据是什么？**（证据）→ 原文卡：条文正文、版本、效力
3. **哪句话靠哪条依据？**（溯源）→ 逐句：点句高亮证据
4. **有没有编造？**（忠实度）→ 判官：逐条断言比对证据

四层全部**如实降级**：拿不到就显示「事后回放 / 整篇粒度 / 未校验 / 未引用法源」，不假装有结论。这是这个项目最核心的取舍——[诊断文档](2026-10-project-diagnosis.md) §6 把每一处降级都写成了待办，本文第 5 节列出仍未闭合的部分。

## 5. 诚实边界（没做到的，写在这里）

1. **判官与被测同族**：忠实度主口径是 glm-5.2 自判；交叉模型（qwen-plus）只在三层评审里验证了 31 条，未接成默认链路。原计划用 deepseek-v4.1-flash，环境无该 key，偏差已记录。
2. **人工层样本小**：25 条（从 66 条候选里分层抽 25，低于原计划的 66 条全判），只能作方向性证据；分类型里 quality 只有 0.846（11/13）。
3. **检索评测已饱和**：六臂消融 Hit@5 全 1.0，**不足以支撑更细的调优结论**（要真调优得先造有区分度的检索集）。
4. **历史记录不回溯**：`references_json[].verification` 是生成当时的快照，回填只写 `evidence_json` 并标 `basis=recomputed`，界面上分开显示。
5. **语料按缺口补，不追全文**：劳动合同法 98 条、劳动争议调解仲裁法 54 条、消费者权益保护法 63 条、民间借贷规定 31 条已全文；其余三部（著作权法 7 条、公司法 12 条、民法典合同编 17 条）**冻结在节选**——对求职 demo 与早期产品，条款数量不是瓶颈，证据链机制才是；产品化时按真实引用缺口补录，不再按“法条总数”铺量。
6. **面板异步化的代价**：面板是懒加载 chunk，首帧右侧先出现预留的 380px 空列（栅格变量预留，不产生布局位移）；离线且未缓存时该 chunk 加载会失败一次，没有面板级重试与提示（只有全局 `OfflineBanner`）。
7. **遗留死 CSS**：`design-tokens.css` 里 18 个 direction B 之前的类已无引用，与在用选择器交织，约 1.4 KB，留作开口项（[step20](step20-bundle-headroom.md) §7）。
8. **合同审查三层评审已闭环，但第三层是 AI 裁决**：`step21` 跑完规则层与双模型裁判（53 条风险里带定位仅 25 条 / 47.2%；glm 有据 7/7、qwen 4/7；质量 pass 5/7 vs 0/7）；`step24` 用 AI 独立复核判完 14 条抽检，得到 glm 一致 13/14、qwen 7/14，并抓出两个裁判在「有据性」轴都放过的摘要虚报。**这不是人工标注**——一致率只说明「裁判像不像这个口径」，不代表「产品像不像真实律师」；样本 7 条记录里 3 条是同一份 18 字合同。合同审查仍缺条级引用与句级溯源。详见 [step21](step21-contract-review-three-layer.md)、[step24](step24-contract-review-adjudication.md)。

9. **证据链口径以服务端为准，门禁只认「有没有定位」**：step25 的徽标读后端下发的 `evidence` / `evidence_summary`（`app/services/legal/contract_evidence.py` 读时计算，不写库），前端 `useContractEvidence` 只在缺字段时回退本地重算，两份实现仍并存。审核通过前会拦「无条款定位」（前端勾选确认 + 服务端 409 兜底），但拦的是**有没有定位**，不是**定位对不对**——snippet 仍是「包含」判断，重复句会误判，真正的定位需要段落偏移；也只拦 approve，退回/转线下/关闭不受影响。
10. **风险只剩 JSON 一份**：step26 把 `contract_risk_items` 合进 `legal_contract_reviews.risks_json`（单表写入、迁移已执行），代价是跨审查的严重度聚合没有索引可用；downgrade 只恢复表结构不恢复数据，旧版本风险随新版本整体替换、不单独留档。
11. **风险统计是读取时聚合**：`risk-stats` 复用 `list_rows` 的 50 条上限，时间维度只有近 7/30 天的粗窗口与按周趋势，没有自定义起止/同比环比；数据量上来后需要物化快照，而不是给 JSON 建索引。
12. **风险处置是追加式记录**：`risk_*` 动作复用审核动作表（`review_stats` 会一起计数）；撤销（reopen）只拉回状态、保留历史，没有逐条历史状态恢复。
13. **提醒是拉取式的**：SLA 只在审核台展示（无推送/升级），24h 阈值写死；咨询证据链摘要只读、不阻断审核。
14. **队列信号只提示不阻断**：无依据咨询仍可通过审核，阈值固定、队列本身不按依据筛选（筛选只在咨询 tab）。
15. **通知是站内一次性的**：无引用咨询提交时提醒审核律师一次（无版本维度、重提不重复），不检查免打扰偏好，也不覆盖 `weak` 等级。
16. **追问对比只对有 `parent_id` 的记录生效**：历史追问无父链接不显示；对比按来源/标题匹配、不比较正文措辞，列表页不展示。
17. **补充完成通知只覆盖「退回后补充」**：普通追问不通知；覆盖率仍是词面重合口径，无重叠时为 `—`；通知失败只记日志。
18. **SLA 提醒依赖 Celery beat**：只提醒已分配审核人、逾期不升级、改期不重置；本地只起 web 时不会自动发。
19. **批量处置只限单条审查内**（无全选、备注固定）；门户概览只读，不暴露审核状态或风险数量。
20. **台账只展示最近一次审查**：关联靠 `source_review_id`，手工合同显示未审查；step44 已把审查状态/风险计数物化到 `legal_contract_review_summaries`，筛选与分页走 SQL（无 1000 条上限），但一致性依赖写入路径刷新——漏刷要跑补数脚本；step45 补了 critical/medium/low 与按审查时间排序，但未审查记录在升降序里都排最后、`risk=medium` 是「有中风险」而非「只有中风险」、按审查时间排序无索引（大数据量会 filesort），且分页仍是 OFFSET。
21. **邮件渠道默认关闭**：需要组织外发策略 + SMTP + worker；受 DLP/审批策略约束，无退订链接；HTML 版式来自内置注册表，数据库覆写有 `layout`（保版式，step40）/`html`/`text` 三种，深链只有一个「审核台」入口、不带记录 id。
22. **投递看板是只读聚合 + 死信重排**：不能批量重排/重发/改内容；趋势是「创建日 + 当前状态」，没有积压深度历史（step41）；`org_id` 只过滤邮件 Outbox；`read/acknowledged` 计入成功侧会抬高成功率；时间窗比较沿用应用侧 UTC，与库时区不一致时边界会偏。
23. **通知模板编辑的边界**：layout 只覆盖 4 个文案字段，改版式仍要改代码；html 正文是管理员输入、不做 HTML 消毒；没有 diff/一键回滚；页面固定 zh-CN；预览用固定示例参数。
24. **告警有升级但仍有盲区**：只发组织管理员（平台账号不收）、阈值全局、冷却窗口边界可能连发两次；step43 补了持续升级与静默时段，但升级仍无值班/转派、静默只能靠 API 配置；告警本身走通知 Outbox，邮件队列积压时告警也会晚到。
25. **积压快照依赖 beat 且只有 5 分钟粒度**：停摆时曲线断裂、不插值；组织曲线只覆盖有管理员的组织；吞吐只算投递成功（`sent_at`），失败不进曲线；非 MySQL/SQLite 方言的小时桶会退回 SQLite 语法。
26. **包体余量见底**：总资产已到预算 99%（1686.1 / 1700 KB），新 tab 已按异步 chunk 拆，但再加页面级 chunk 会触顶——下一步要么拆共享依赖，要么提高预算并写清理由。
