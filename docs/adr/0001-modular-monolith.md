# ADR-0001：模块化单体（Modular Monolith）

- **状态**：已采纳
- **日期**：2026

## 背景

项目规模为后端 ~51k 行 Python、前端 69 个源文件，功能完整但 `services/`/`api/`
平铺、存在循环依赖与上帝文件。可选路径：拆微服务、完整 DDD 重写、或模块化单体。

## 决策

保持单一 FastAPI 进程，按业务域纵向切片为「有界上下文」，域内
`api / service / model` 内聚，域间只通过 service 门面通信。

## 理由

- 团队规模与部署复杂度不支撑微服务的独立部署、服务发现与分布式事务成本。
- 完整 DDD 重写风险高、周期长，且无法「小步提交、行为保持」。
- 模块化单体以「强边界 + 依赖红线」即可获得高内聚低耦合，且每步可回归验证。

## 后果

- 域边界成为长期约束，新增跨域能力必须走门面，禁止 import 他域内部实现。
- 未来若某域确需独立扩展，可从该域边界平滑拆出为服务（已预留 `repositories/` seam）。
