# ADR-0007：工作台记录可见性——从个人隔离到案件级协作

- **状态**：已采纳
- **日期**：2026-10-11

## 背景

工作台的咨询 / 合同审查 / 文书记录最初按"个人工作台"建模：`legal_workspace_service`
的 `get_row` / `list_rows` 一律 `WHERE user_id == 当前用户`，非本人读取返回 404。

后续叠加的"审核"场景天然跨用户：审核队列的 `apply_review_action` / `assign_reviewer` /
`add_review_comment` 走 `target_query` + 审核律师鉴权，**不**按 `user_id` 过滤。于是出现口径
矛盾——审核律师能"审"他人记录、却打不开其**详情**（从组织/案件级入口点进去 `get_row` 返回
404）；另有 drafts 协作路径用了 `owner ∪ reviewer ∪ admin` 的第三套判据。读详情与审核动作
可见性不一致，属"个人工作台模型 vs 团队协作模型"的架构取舍。

## 决策

分两步落地，统一到"记录可见性继承其案件的访问策略"。

**A（最小一致化）**：`get_row` 非本人读取放开给 被指派审核人 / 平台管理员 / 与所有者同组织的
审核律师；关联案件再叠 `verify_case_access`；其余按"不存在"（防枚举）。记录无 `organization_id`，
经所有者推导组织以防跨组织越权。

**B（案件级协作）**：
- `get_row`：归属某案件的记录，凡能访问该案件者可读——`verify_case_access`（普通模式=组织成员、
  严格模式=案件成员）；平台管理员与被指派审核人亦可。**孤立记录（无 `case_id`）回退 A**。
- `list_rows`：带 `case_id` 的案件上下文列表返回**该案件下全体成员记录**（调用者须能访问该案件）；
  **无 `case_id` 的个人工作台默认视图维持 `user_id` 隔离**，不泄漏他人记录；案件维度行附
  `submitter_name` 供前端标注提交人。
- **写操作不扩权**：编辑 / 删除 / 送审仍按原 owner / 审核律师鉴权。可见 ≠ 可改。

## 理由

- 复用既有 `verify_case_access` 的案件访问模型，**无需 schema 迁移**，记录可见性与案件访问
  一致。
- 兼顾隐私（个人默认视图隔离）与协作（案件上下文内共享）。
- 最小权限：写不扩权、未授权一律 404 防枚举。

## 后果

- 读（详情 / 列表）以"案件访问权"为准；孤立记录仍仅 owner + 审核律师可见——鼓励先用 L-17
  「归入案件」归档再协作。
- **个人工作台默认视图必须保留 `user_id` 维度**，这是 B 的核心正确性约束，严禁回归成全量可见。
- 前端案件上下文列表须展示提交人（已加 `submitter_name` + 「提交人」列/行内标注），否则律师
  会困惑"这条不是我提的"。
- 覆盖测试：`tests/test_legal_workspace_visibility.py`（A）、
  `tests/test_legal_workspace_case_sharing.py`（B，含严格模式与跨组织门禁）。
